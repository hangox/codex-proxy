### Responses compaction v2 探针

- 本地路由：`POST /v1/responses`

**同一个账号、同一个模型，走普通 Responses 路径能正常压缩，而专用的 v1 端点

## 根因

`src/proxy/codex-api.ts` 当时仍然按 remote compaction v1 打：

`/codex/responses/compact`

而当前上游是通过普通 `/codex/responses` 走 v2 流程：input 末尾带一个
`compaction_trigger` item，返回一个加密的 `compaction` output item。proxy 的
opaque compact bridge 没有实现这条流程。

时间线也支持「上游能力/协议切换」而非本地回归：同一个长期运行的进程在 01:16
之前一直能成功压缩，02:33 起 `gpt-5.6-sol` 和 `gpt-5.6-luna` 同时开始从 v1
端点收到快速 404。

## 已实施的修复

`src/proxy/codex-api.ts` 改为走 remote compaction v2：

1. 通过普通的 Responses 传输发送 compact input；
2. 在 input 末尾追加 `compaction_trigger` item；
3. 沿用 compact 请求的 metadata / identity header；
4. 从流里收集 output item、从 `response.completed` 收集 usage；
5. 要求恰好一个 `compaction` output item；
6. 在与当前 Codex 相同的约 64K token 预算内于客户端侧保留 user 消息，再把
   加密的 compaction item 接在末尾；
7. 把装配好的历史和 usage 转换成既有的 `CodexCompactResponse` 契约；
8. 主动声明 `x-codex-beta-features: remote_compaction_v2`（官方客户端每次都带），
   即能力协商是**声明式**的。

同时修正了取消路径：已 abort 的 WebSocket 请求不会再发起第二次 HTTP 请求。

### 关于「自动回落 v1」：**已删除，不要再加回来**

最初的实现里有一条「上游明确表示不支持 trigger 时自动回落 v1」。这条后来被
整个删掉了，原因不是它写得不好，而是这个方向本身是错的：

- **回落的目标端点当前本身就是 404**（就是本文档记录的这次事故）。回落到一个
  确定失败的端点，期望价值不是「降级可用」而是负的——白发一次请求，并且把
  真实失败原因替换成 v1 的 Not Found。
- 判据只能来自上游的错误文案，而「从错误文案反推上游支不支持某能力」是错的
  抽象。实测过一条 `Invalid value for 'input': compaction_trigger must be the
  last input item`——这是**位置放错、请求构造 bug**，却同时命中 `invalid` 和
  `compaction_trigger` 两个关键词被判成「v2 不可用」，于是客户端最终看到 404，
  而上游真实原因是 400 参数错。
- 代价不对称：误判「不支持」= 白花一次 compact + 掩盖真因；误判「支持」=
  一次明确报错。后者便宜得多。
- 特别地，**404 在这里不可能意味着「v2 不被支持」**：`/codex/responses` 是所有
  普通请求都在打的端点。它返回空 body 404 的真实含义是 Cloudflare path-block，
  吞掉会让清 cookie / 计数 / 到阈值禁用账号那套自愈延迟一次浪费请求才触发。

取而代之的是显式配置键 `model.compact_protocol`（`auto` | `v1` | `v2`，默认
`auto` = 纯 v2 无回落）。上游真回滚时改一个配置键即可，不需要发版；这也是
`createCompactResponseV1` 被保留下来的唯一理由。该键可从受鉴权的
`/admin/general-settings` 读回实际生效值（CLAUDE.md 记的「未知配置键被 Zod
静默丢弃」那条坑的硬性要求）。
